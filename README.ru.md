Прокси-балансировщик, который сам выясняет, какой из ваших прокси лучше
работает с каким сайтом, и распределяет трафик по этим измерениям.
Один бинарник, без зависимостей, с веб-панелью внутри.

```
fairway -proxy :7770 -admin 127.0.0.1:7771
```

## Установка

### Linux-сервер (systemd)

`install.sh` ставит fairway systemd-сервисом на RHEL, Rocky, Alma, Fedora,
Debian и Ubuntu. Скрипт скачивает бинарник из релиза под архитектуру машины и
сверяет его с `SHA256SUMS`, заводит системного пользователя `fairway`, держит
конфиг в `/etc/fairway`, данные в `/var/lib/fairway` и запускает сервис.

```
curl -fsSLO https://raw.githubusercontent.com/Crasher69/fairway/main/install.sh
sudo bash install.sh
```

Сервис слушает все интерфейсы: прокси на порту `7770`, панель на `7771`
(стандартные порты проекта). В конце скрипт печатает адрес прокси
для клиентов и ссылку на панель с токеном. Полезные опции (полный список
в `--help`):

```
sudo bash install.sh --proxy :3128                  # другой порт прокси
sudo bash install.sh --admin 127.0.0.1:7771         # панель только с самого сервера
sudo bash install.sh --open-firewall                # открыть порты в firewalld/ufw
sudo bash install.sh --allow-from 203.0.113.0/24    # ...или только для одной сети
sudo bash install.sh --download                     # обновиться до последнего релиза
sudo bash install.sh --version v0.3.0               # конкретный релиз
sudo bash install.sh --uninstall                    # удалить сервис, конфиг и данные остаются
```

Обновление сохраняет порты из уже установленного юнита и не трогает конфиг.

Свежая установка сразу работает как обычный прокси: конфиг, который fairway
создаёт при первом запуске, содержит `allow_direct: true`, и пока не заведены
прокси и правила, трафик уходит напрямую с сервера. Прокси открыт всем, кто
достучится до порта; как его закрыть — в разделе [Безопасность](#безопасность).

### Бинарники

Готовые бинарники лежат на
[странице Releases](https://github.com/Crasher69/fairway/releases/latest):
`fairway-linux-amd64`, `fairway-linux-arm64`, `fairway-windows-amd64.exe`,
`fairway-darwin-arm64` (Apple Silicon), `fairway-darwin-amd64` (Intel Mac).
Статические, без зависимостей: скачал и запустил. Последняя сборка всегда
доступна по прямой ссылке, например:

```
curl -LO https://github.com/Crasher69/fairway/releases/latest/download/fairway-linux-amd64
chmod +x fairway-linux-amd64
./fairway-linux-amd64 -proxy :7770 -admin 127.0.0.1:7771
```

Запущенный так, fairway держит `config.json` и `data/` в текущем каталоге.
Есть ещё [Docker-образ](#docker), или соберите из исходников, см.
[Сборка](#сборка).

## Быстрый старт

1. **Откройте панель** по ссылке с токеном из лога (для сервиса —
   `journalctl -u fairway -n 50`): `http://server:7771/?token=…`. Задайте
   пароль на вкладке «Доступ», чтобы после перезапуска не искать токен.
2. **Настройте клиентов на прокси.** Fairway — HTTP-прокси (обычный HTTP и
   `CONNECT` для HTTPS):

   ```
   curl -x http://server:7770 https://example.com/
   export HTTPS_PROXY=http://server:7770 HTTP_PROXY=http://server:7770
   ```

   В браузере укажите его как HTTP- и HTTPS-прокси в сетевых настройках.
   Пока прокси не заведены, трафик уходит напрямую с сервера.
3. **Заведите прокси** на вкладке «Прокси»: по одному или целой закупкой
   через импорт списком (`ip:port:логин:пароль`, `socks5://user:pass@host:port`
   и другие ходовые форматы).
4. **Соберите лист** на вкладке «Листы» и отметьте в нём нужные прокси.
5. **Добавьте правила доменов** на вкладке «Домены»: какой лист обслуживает
   какой сайт. Чтобы балансировать вообще весь трафик, укажите лист в
   `defaults.list` или заведите правило `*`.

Через несколько запросов на вкладке доменов видно, какие прокси обслуживают
каждый сайт, их цену и долю трафика.

## Безопасность

По умолчанию прокси открыт: им может пользоваться любой, кто достучится до
порта, а с `allow_direct: true` домены без правила уходят с IP самой машины.
Так задумано, чтобы свежая установка работала сразу. Закрыть его:

- **Авторизация на прокси.** На вкладке «Доступ» включите логин и пароль для
  прокси (`proxy_auth` в конфиге). Клиенты тогда передают
  `Proxy-Authorization: Basic`: браузер спросит их сам, в приложениях они
  указываются в адресе, `http://login:password@server:7770`.
- **Прямой трафик.** Поставьте `"allow_direct": false` в `defaults`: домен без
  правила получит 503, а не уйдёт с вашего реального IP.
- **Firewall.** Откройте порты только своим клиентам:

  ```
  sudo ufw allow proto tcp from 203.0.113.0/24 to any port 7770          # Ubuntu/Debian
  sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" \
       source address="203.0.113.0/24" port port="7770" protocol="tcp" accept' \
       && sudo firewall-cmd --reload                                      # семейство RHEL
  ```

  То же для обоих портов делает `install.sh --allow-from CIDR`.

**Панель** на адресе не loopback пускает любого, у кого есть ссылка с токеном
или пароль; fairway предупреждает об этом в логе. Задайте пароль и не
выкладывайте ссылку с токеном в общие логи. Чтобы панель была доступна только
с сервера, поставьте `--admin 127.0.0.1:7771` и ходите через SSH-туннель:
`ssh -L 7771:127.0.0.1:7771 user@server`.

**Docker обходит ufw:** порт, опубликованный как `-p 7770:7770`, доступен
снаружи, даже если ufw его запрещает. Публикуйте его на конкретном адресе
(`-p 10.0.0.5:7770:7770`) или фильтруйте в цепочке `DOCKER-USER`.

**Корневой ключ MITM** (`data/fairway-ca.key`) позволяет подписывать
сертификаты, которым доверяет вся ваша сеть; см. [MITM](#mitm-смотреть-запросы).

## Чем отличается от gost, glider, 3proxy и Squid

Те умеют списки и ротацию, но балансируют статически: round-robin, least-conn
или заданные вручную веса. Fairway копит статистику на **пару (домен, прокси)**
и пересчитывает её на каждом запросе.

Практическая разница: один и тот же прокси может быть быстрым для одного сайта
и полумёртвым для другого, а на третьем — забаненным. Fairway это видит и
разводит трафик сам.

## Как он выбирает

Все метрики сводятся к одному числу — **цене**: сколько секунд занял бы через
этот прокси эталонный ответ в 64 КБ.

```
цена = (время подключения + время до первого байта) + 64КБ / скорость
цена /= (1 - доля ошибок)²
```

Дальше — лотерея с весом `(1/цена)²`, плюс 10% запросов уходит на разведку:
без неё лидер забрал бы весь трафик, а о том, что аутсайдер починился, узнать
было бы неоткуда.

**Медленный прокси остаётся в ротации с низким весом. Забаненный выключается
совсем — но только для того домена, где его забанили.** Признаки бана:
HTTP 403, 429, 451, 407, три ошибки соединения подряд или страница проверки
вместо содержимого (в режиме MITM). Прокси, который принял соединение и не
передал от цели ни байта, тоже считается ошибкой соединения: цель обязана
ответить за время dial-timeout.

**Запрос, оставшийся без ответа через один прокси, повторяется через
другой**, всего до трёх прокси, и клиент этого не замечает. Для туннелей
повторяется всё, что клиент прислал до первого байта от цели (включая
TLS-рукопожатие), для обычного HTTP — запросы без тела. В режиме MITM
апстрим меняется прямо посреди туннеля: клиент говорит по TLS с нами, а не
с целью. Как только от цели пришёл хоть байт, запрос не повторяется: он мог
быть уже выполнен.

Рейтинги переживают перезапуск (`data/ratings.json`).

## Язык

По умолчанию лог и панель на английском. Переключатель в шапке панели
меняет язык и в панели, и в логе: выбор сохраняется в конфиге полем
`"language": "ru"` и переживает перезапуск. Флаги командной строки всегда
на английском: они разбираются раньше, чем прочитан конфиг.

## Конфиг

Создаётся при первом запуске, перечитывается на лету — перезапуск не нужен.
Битая правка не применяется: в работе остаётся предыдущая версия.

```json
{
  "language": "en",
  "defaults": {
    "list": "residential",
    "allow_direct": false,
    "max_conns_per_proxy": 32,
    "ban_duration": "5m"
  },
  "proxies": [
    {
      "name": "p1",
      "scheme": "socks5",
      "host": "1.2.3.4",
      "port": 1080,
      "login": "user",
      "password": "pass",
      "country": "RU",
      "comment": "куплен до декабря"
    },
    {"name": "p2", "scheme": "http", "host": "5.6.7.8", "port": 3128}
  ],
  "lists": [{"name": "residential", "proxies": ["p1", "p2"]}],
  "domains": [
    {"pattern": "example.com", "list": "residential", "max_parallel_proxies": 3},
    {"pattern": "*.example.com", "list": "residential", "mitm": true}
  ]
}
```

Два лимита легко перепутать:

- `max_parallel_proxies` — сколько **разных** прокси листа работают на домен
  одновременно;
- `max_conns_per_proxy` — сколько соединений держит **один** прокси.

`0` означает «взять из `defaults`», `-1` — «без ограничения».

Правило подбирается от частного к общему: точное имя → самый длинный
`*.суффикс` → `*` → `defaults.list`.

С `allow_direct: false` домен без правила получит 503, а не уйдёт молча
с вашего реального IP. Отсутствующее поле значит `false`; конфиг, который
fairway пишет при первом запуске, ставит `true`, чтобы свежая установка сразу
работала как обычный прокси.

Поддерживаются апстримы `http://`, `https://`, `socks5://` и `direct`.

Листы держат прокси по `id` — UUID, который fairway выдаёт каждому прокси сам
и дописывает в файл при первом чтении. Поэтому прокси можно переименовывать,
листы от этого не ломаются. В файле, который правите руками, в листе можно
писать и имя прокси: при загрузке оно заменится на его `id`, и конфиги
из прошлых версий переходят на id без потери привязок.

## Панель

По умолчанию на `127.0.0.1:7771`. Внутрь ведут два пути, и работают оба:
ссылка с токеном, которую fairway печатает в лог при запуске, и пароль,
заданный на вкладке «Доступ». Пароль лежит в конфиге хешем PBKDF2 и переживает
перезапуск, в отличие от токена: тот при каждом запуске новый, если не
закреплён флагом `-admin-token`.

Показывает по каждому домену: какие прокси его обслуживают, их задержки,
скорость, долю ошибок, ожидаемую долю трафика и статус («ок», «деградирует»,
«забанен до 14:32»), живой лог запросов и график задержек с подсказкой при
наведении. Бан можно снять одной кнопкой, не дожидаясь срока. Пустая панель
показывает, с чего начать, и адрес прокси для настроек браузера.

Тема светлая; тёмная включается по системной настройке или кнопкой в шапке.

Настройки разнесены по вкладкам: **Прокси** (адрес, порт, логин, пароль,
страна, комментарий; отмеченные галочками можно разом удалить, положить в
лист или убрать из него), **Листы** (набор прокси галочками из уже
заведённых; лист можно переименовать — ссылки в правилах обновятся сами)
и **Домены** (правило и лист выпадающим списком). Изменения сохраняются
в конфиг и применяются сразу. Есть кнопка перечитать файл, если правили
его руками.

Строку из прайса поставщика — `socks5://user:pass@1.2.3.4:1080` — можно
вставить прямо в поле адреса, она разложится по полям. А целую закупку —
в импорт списком: понимает `ip:port:логин:пароль` и прочие ходовые форматы,
сам присваивает имена, пропускает дубликаты и показывает, какая строка
не разобралась. Импортированное можно сразу положить в лист.

В таблицах есть поиск, в выборе прокси для листа — тоже: с полусотней
апстримов без него не обойтись.

## MITM: смотреть запросы

Опционально Fairway расшифровывает HTTPS, как Fiddler или Charles: выпускает
собственный корневой сертификат, а сертификаты сайтов подписывает им на лету.

```
fairway -export-ca fairway-ca.crt
```

Полученный файл импортируется в «Доверенные корневые центры» на машинах сети
(в домене — групповой политикой). Включается правилом `"mitm": true`.

Зачем это балансировщику: без расшифровки в туннеле видно только байты, и 403
неотличим от медленного ответа. С расшифровкой видно настоящий HTTP-статус,
а значит, бан детектируется точно. Заодно видно тело: если сайт вместо
содержимого отдал страницу проверки Cloudflare, DataDome, Яндекса или
капчу, прокси для этого домена банится так же, как по 403, хотя статус
был 200.

Что нужно знать заранее:

- **Certificate pinning.** Банковский и мобильный софт проверяет не цепочку,
  а конкретный сертификат — через MITM он не подключится. Для таких доменов
  ставьте `"mitm": false`, туннель останется прозрачным.
- **Проверка отзыва.** У приватного CA нет CRL и OCSP. Браузеры для приватных
  корней отзыв не проверяют, а вот `curl` на Windows падает с
  `CERT_TRUST_REVOCATION_STATUS_UNKNOWN` — лечится `--ssl-no-revoke`.
- **Firefox, Java и Python** держат своё хранилище сертификатов, CA туда
  добавляется отдельно.

Корневой ключ (`data/fairway-ca.key`) — самое ценное, что есть у установки:
кто его получит, сможет подписывать сертификаты, которым доверяет вся ваша
сеть. Права на файл 0600, каталог данных наружу не отдавайте.

## Docker

```
docker run -d --name fairway \
  -p 7770:7770 -p 127.0.0.1:7771:7771 \
  -v fairway-data:/data \
  ghcr.io/crasher69/fairway
```

Образы под `linux/amd64` и `linux/arm64` публикуются в GitHub Container
Registry на каждый релиз. Собрать локально: `docker build -t fairway .`

Образ собран на `scratch`, внутри бинарник, корневые сертификаты и часовые
пояса. Панель наружу пробрасывайте только на `127.0.0.1`. Docker публикует
`-p 7770:7770` на всех интерфейсах в обход ufw: прочитайте
[Безопасность](#безопасность), прежде чем запускать его на публичном сервере.

## Производительность

На локальном стенде (всё на одной машине, Windows, ответы по 20 КБ, один
проход через fairway с апстримом `direct`):

| режим | 100 соединений | 500 соединений |
|---|---|---|
| CONNECT-туннели | 65 000 запр/с, 1,2 ГБ/с | 61 000 запр/с |
| обычный HTTP | 37 000 запр/с, 700 МБ/с | 33 000 запр/с |
| MITM (с расшифровкой) | 6 900 запр/с, 130 МБ/с | 6 700 запр/с |

Туннель стоит две горутины и около 40 КБ кучи; 500 MITM-туннелей занимают
157 МБ из-за буферов TLS с обеих сторон. Обычный HTTP идёт через пул
keep-alive соединений к цели. Стенд собирается целиком из этого репозитория
(`cmd/benchtarget`, `cmd/loadgen`); методика и подробности в
[docs/BENCHMARK.md](docs/BENCHMARK.md).

## Сборка

Нужен только Go, ничего больше — ни cgo, ни сборки фронта.

```
go build ./cmd/fairway          # под текущую систему
./build.sh 1.0.0                # релизные бинарники под linux, windows, macOS
go test ./...
go generate ./cmd/fairway       # перерисовать иконку (после правки internal/brand)
```

Иконка у Windows-сборки зашита в exe: ресурс собирается своим кодом в
`internal/brand`, без внешних утилит, и уже лежит в репозитории.
