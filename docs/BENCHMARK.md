# Нагрузочный тест

Замер 2026-09-09. Стенд собирается из одного репозитория, сторонних утилит
не нужно:

```
go run ./cmd/benchtarget -addr 127.0.0.1:19005 -size 20000 -tls   # цель по HTTPS
go run ./cmd/benchtarget -addr 127.0.0.1:19006 -size 20000        # цель по HTTP
fairway -proxy 127.0.0.1:29081 -admin 127.0.0.1:29181 -config bench.json -insecure-origin
go run ./cmd/loadgen -proxy 127.0.0.1:29081 -target https://127.0.0.1:19005/ -insecure -c 100 -d 12s -keep-alive
go run ./cmd/loadgen -proxy 127.0.0.1:29081 -target http://127.0.0.1:19006/ -c 100 -d 12s -keep-alive
```

`bench.json` — один прокси `direct`, баны выключены, лимит соединений снят:

```json
{
  "defaults": {"list": "lab", "allow_direct": false, "max_conns_per_proxy": -1, "ban_duration": "0s"},
  "proxies": [{"name": "direct", "url": "direct"}],
  "lists": [{"name": "lab", "proxies": ["direct"]}],
  "domains": []
}
```

Для MITM добавляется правило `{"pattern": "127.0.0.1", "list": "lab", "mitm": true}`
(можно на лету из панели). Флаг `-insecure-origin` нужен только потому, что
цель с самоподписанным сертификатом; в бою его не ставить.

**Стенд:** Windows 11, всё на одной машине — генератор, fairway и цель. Тело
ответа 20 КБ, 12 секунд на точку, между точками пауза до разгрузки TIME_WAIT.
Замеряется сам fairway с апстримом `direct`, то есть один проход через
балансировщик: именно столько он добавляет к пути запроса.

## Как читать

**Туннели** — основной сценарий (HTTPS без расшифровки). По две горутины на
туннель, по одной на направление копирования, и по 40 КБ кучи на туннель.
Задержка p50 в 1 мс — это loopback, в бою её задаст апстрим.

**Обычный HTTP** идёт через пул keep-alive соединений к цели: за 12 секунд и
446 тысяч запросов на стенде осталось 95 сокетов в TIME_WAIT. Он вдвое
медленнее туннелей, потому что на каждый запрос разбирается HTTP и копируется
тело через `http.Transport`, а туннель — это `io.Copy`. Горутин на соединение
больше (Transport держит свои читающую и пишущую), отсюда 4 257 на 1000.

**MITM** — два TLS-соединения на туннель, разбор HTTP и просмотр первых
64 КБ тела на каждый запрос. Отсюда в 9 раз меньше запросов в секунду и
157 МБ кучи на 500 туннелях: буферы TLS с обеих сторон. Зато один поток на
туннель: 512 горутин на 500. При 500 соединениях p99 растёт до полусекунды —
рукопожатия TLS и разбор конкурируют за процессор с генератором на той же
машине.

**Отказы на 500 и 1000 соединениях** — не обрывы работающих туннелей, а
неудачные попытки открыть новые: `connectex: refused`. Генератор поднимает
тысячу соединений залпом, очередь accept на Windows переполняется, и часть
SYN уходит в повторы на секунды (отсюда «максимум 11 с»). На 1000 соединениях
живой остаётся примерно половина, что видно по горутинам. Это ограничение
стенда на одной машине; проверять тысячи туннелей нужно на Linux с
разнесёнными ролями.

## Что изменилось с прошлого замера

Прошлые замеры (7–8 сентября) шли через отдельный минимальный апстрим-прокси
из старых заметок, которого нет в репозитории, и он закрывал соединение к цели
после каждого запроса. Поэтому те цифры (36 000 на туннелях, 14 000 на HTTP)
несравнимы с этими: теперь мерится один проход через fairway с апстримом
`direct`, и стенд воспроизводим целиком из `cmd/`.

Из правок кода на цифры повлияли две:

- **пул соединений к цели для обычного HTTP** (`Upstream.Transport`): без
  него каждый запрос открывал новое соединение и упирался в эфемерные порты;
- **лимит простаивающих соединений пула поднят с 64 до 256 на хост**: при 100
  клиентах лишние соединения закрывались и за прогон копилось 24 тысячи
  TIME_WAIT, теперь их 95.

## Чего этот замер не показывает

- Реальные апстрим-прокси в интернете: там задержка в десятки и сотни
  миллисекунд, и упрёмся мы в них, а не в fairway.
- Поведение на Linux и на нескольких машинах: отказы на 500+ соединениях —
  артефакт стенда, а не прокси.
