# mitm — адаптивный прокси-балансировщик с MITM

Один статический бинарник на Go: HTTP/HTTPS прокси-сервер, который распределяет
исходящие запросы по пулу апстрим-прокси, сам измеряет их качество для каждого
домена и балансирует на основе этих метрик. Опционально расшифровывает TLS
(собственный CA, как Fiddler) — для просмотра запросов и точных метрик.

## Зачем это (чего нет в готовых решениях)

gost / glider / 3proxy / Squid умеют списки и ротацию, но балансируют статически
(round-robin, least-conn, фиксированные веса). Здесь ключевое — **адаптивный
рейтинг на пару (домен, прокси)**, который сам себя настраивает в рантайме.
Один прокси может быть быстрым для одного сайта и забаненным на другом.

## Модель данных

- **Proxy** — апстрим: схема (http/https/socks5), host:port, креды, метки.
- **List** — именованный набор прокси.
- **Domain** — правило: домен (+ wildcard) → List + настройки:
  - `max_parallel_proxies` — сколько РАЗНЫХ прокси работают на домен разом,
  - `max_conns_per_proxy` — сколько соединений держит один прокси,
  - `mitm: true|false` — расшифровывать или просто туннелировать,
  - `ban_duration` — на сколько выключать прокси после бана.
- **Stats(domain, proxy)** — живут в памяти, периодически сбрасываются на диск:
  connect time, TTFB, throughput, error rate — всё как **EWMA**
  (экспоненциальное скользящее среднее: само забывает старое, память O(1)).

## Алгоритм выбора прокси (`internal/rating`)

Всё сводится к одному числу — **цене**: сколько секунд занял бы через этот
прокси эталонный ответ в 64 КБ.

```
цена = (connect + TTFB) / 1000 + 65536 / скорость
цена /= (1 - доля_ошибок)^2        # ошибки дороже медленности:
                                   # неудачный запрос придётся повторять
```

Все слагаемые — EWMA (alpha 0.25): O(1) памяти на пару, само забывает старое,
чистить нечего. Скорость считается только по ответам **от 32 КБ** — на мелких
тело приходит вместе с первым байтом, знаменатель вырождается и скорость
скачет от нуля до сотен МБ/с.

Порядок выбора:

1. **Забаненные для домена выбывают** целиком.
2. **Непроверенные идут первыми** (меньше 3 замеров). Без этого новый прокси
   не набрал бы статистику и остался бы невидимым навсегда.
3. **Разведка**: с вероятностью `Epsilon` (10%) — случайный из живых.
4. Иначе — **взвешенная лотерея** с весом `(1/цена)^Sharpness`, где
   `Sharpness = 2`.

Почему лотерея, а не «всегда лучший»: победитель забрал бы весь трафик,
упёрся в лимит соединений и деградировал, а его замеры перестали бы отражать
реальность. Почему степень, а не просто `1/цена`: при линейном весе прокси
вдвое дешевле получает лишь вдвое больше запросов — для «выбираем лучшее»
этого мало. Квадрат даёт лидеру ~90% трафика, остальное уходит на разведку.

**Бан ≠ медленно.** Медленный прокси остаётся в ротации с низким весом.
Выключается он только по признакам «мёртв для этого домена»:

- HTTP 403, 429, 451, 407 → бан на `ban_duration`;
- 3 ошибки соединения подряд → бан (успех обнуляет серию).

Бан всегда **только для своего домена**. Капча пока не детектируется — для неё
нужно видеть тело ответа, то есть этап 4 (MITM).

Рейтинги переживают перезапуск: `data/ratings.json`, автосохранение раз в 30 с
и при остановке, запись атомарная (во временный файл + rename). Протухшие баны
при загрузке не восстанавливаются.

## Как узнаём домен

- Обычный HTTP — заголовок `Host`.
- HTTPS без MITM — из `CONNECT host:443`. Дальше видим только байты, поэтому
  метрики = время до первого байта от апстрима + bytes/sec через туннель.
- HTTPS с MITM — видим настоящий HTTP: метод, URL, заголовки, тело, статус.
  Отсюда точный детект бана и per-response метрики.

## MITM (`internal/mitmca`, `internal/forward/mitm.go`)

1. При первом запуске в каталоге данных создаётся корневой CA:
   `fairway-ca.pem` (раздаётся) и `fairway-ca.key` (права 0600).
2. На `CONNECT` с правилом `mitm: true` отвечаем `200 Connection established`,
   поднимаем TLS с клиентом и по SNI на лету выпускаем сертификат домена,
   подписанный нашим CA.
3. Расшифровали → разобрали HTTP → отдельным TLS-соединением через выбранный
   апстрим идём к цели → ответ отдали клиенту и сняли замер с настоящим статусом.

**Имя CA** — `CN=Fairway Local Root CA (<машина>)`, `O=Fairway Proxy`.
Три требования, и все три обязательны: видно продукт, видно что центр
**локальный**, видно машину выпуска (иначе две установки дадут одинаково
названные, но разные CA, и админ не разберётся). Мимикрия под настоящие
удостоверяющие центры недопустима — это превращает инструмент во вредоносный.

**Ключи — ECDSA P-256.** Ключ листа генерируется один раз при старте и
переиспользуется для всех доменов: генерация ключа на каждое рукопожатие
добавляла бы задержку на ровном месте. Так делают все MITM-прокси.
Сертификаты доменов живут в LRU-кэше на 2048 записей.

**Одно клиентское соединение — одно соединение к цели.** Пула нет намеренно:
HTTP/1.1 внутри соединения последователен, зато замеры точные. ALPN с обеих
сторон ограничен `http/1.1` — HTTP/2 здесь не разбирается.

Известные ограничения:
- **Certificate pinning** — банковский и мобильный софт не пройдёт.
  Отсюда per-domain переключатель `mitm: false` → прозрачный туннель.
- **Проверка отзыва.** У приватного CA нет CRL и OCSP, и клиенты, которые
  требуют проверку отзыва, будут ругаться: `curl` на Windows (schannel) падает
  с `CERT_TRUST_REVOCATION_STATUS_UNKNOWN`, лечится `--ssl-no-revoke`.
  Браузеры для приватных корней отзыв не проверяют и работают нормально.
- **Firefox, Java, Python** имеют своё хранилище сертификатов — CA туда
  добавляется отдельно (в Firefox есть флаг доверять системному хранилищу).
- Раскатка CA по сети: `fairway -export-ca fairway-ca.crt` → Windows
  «Доверенные корневые центры», в домене — групповой политикой.
- **На keep-alive соединении время установки не измеряется** — замер помечается
  `Reused`, и ноль не попадает в среднее время подключения.


## Конфиг (`config.json`)

Создаётся автоматически при первом запуске, перечитывается на лету
(`internal/config.Watcher`, опрос mtime+size раз в 2 с). Битая версия **не
применяется**: в работе остаётся предыдущая, ошибка пишется в лог один раз.

```json
{
  "defaults": {
    "list": "residential",
    "allow_direct": false,
    "max_parallel_proxies": 0,
    "max_conns_per_proxy": 32,
    "mitm": false,
    "ban_duration": "5m"
  },
  "proxies": [
    {"name": "p1", "url": "socks5://user:pass@1.2.3.4:1080", "tags": ["ru"]}
  ],
  "lists": [{"name": "residential", "proxies": ["p1"]}],
  "domains": [
    {"pattern": "example.com", "list": "residential", "max_parallel_proxies": 3},
    {"pattern": "*.example.com", "list": "residential", "mitm": true}
  ]
}
```

Что важно знать про семантику:

- **Два разных лимита, их легко перепутать.** `max_parallel_proxies` — сколько
  РАЗНЫХ прокси листа работают на домен одновременно (рабочий набор);
  `max_conns_per_proxy` — сколько соединений держит один прокси (чтобы не
  задушить лидера рейтинга).
- **Наследование:** `0` — «не задано, взять из `defaults`», `-1` — «явно без
  ограничения». Для `mitm` то же самое даёт отсутствие поля (`null`).
- **Подбор правила:** точное имя → самый длинный `*.суффикс` → `*` →
  `defaults.list`. Регистр и точка в конце FQDN не важны. `*.example.com` не
  покрывает сам `example.com`.
- **`allow_direct`** разрешает ходить напрямую, когда правило не подобрано.
  По умолчанию `false`, и это осознанно: иначе домен без правила молча уйдёт
  с реального IP. При `false` такой запрос получает 503.
- **Неизвестные поля запрещены** (`DisallowUnknownFields`): опечатка в имени
  ключа не должна молча игнорироваться.
- `-upstream host:port` (флаг, можно повторять) собирает временный конфиг
  из командной строки и полностью игнорирует файл — для быстрой проверки.

Прокси при hot-reload сопоставляются **по имени**: если имя и адрес не
изменились, объект переиспользуется вместе со счётчиками и (с этапа 3)
рейтингом. Поэтому переименование прокси = сброс его статистики.

## Админка

Тот же процесс и тот же бинарник:
- REST: `/api/proxies`, `/api/lists`, `/api/domains`, `/api/stats/{domain}`
- реалтайм: SSE или WebSocket, пуш состояния (рейтинги и так в памяти → просто
  сериализуем структуру)
- страница домена: таблица прокси (вес, активные коннекты, connect/TTFB/throughput,
  % ошибок, статус «ок / деградирует / забанен до 14:32»), живой лог запросов,
  графики за последние N минут (кольцевой буфер в памяти)
- фронт без сборки: ванильный JS + uPlot (или HTMX + Alpine), файлы в `web/static`,
  вшиты через `//go:embed` → на выходе по-прежнему один файл.

**Безопасность по умолчанию: админка слушает только 127.0.0.1 + токен/basic-auth.**
Панель управления прокси не должна торчать в интернет.

## Структура

```
cmd/mitmproxy/     main.go, флаги, запуск
internal/config/   модель конфига, загрузка, hot-reload
internal/proxypool/ прокси, листы, EWMA-метрики, алгоритм выбора, семафоры
internal/mitmca/   генерация CA, выпуск сертов на лету, кэш
internal/forward/  CONNECT-туннель, HTTP-форвардинг, диалер через апстрим
internal/stats/    кольцевые буферы, агрегация для админки
internal/admin/    REST API, SSE, embed фронта
web/static/        HTML/JS/CSS админки
docs/              заметки по архитектуре
```

## Правила проекта

- **Только стандартная библиотека там, где это разумно.** Зависимости — по
  необходимости и с оглядкой на кросс-компиляцию.
- **Никакого cgo.** Если понадобится SQLite — только `modernc.org/sqlite`
  (чистый Go). Для MVP хватит JSON-файлов.
- Хранение конфига и снапшотов рейтингов — JSON на диске, hot-reload без рестарта.

## Команды

```
go run ./cmd/mitmproxy          # запуск
go build ./cmd/mitmproxy        # сборка .exe под Windows
go vet ./... && gofmt -l .      # проверки перед коммитом
GOOS=linux GOARCH=amd64 go build -o mitmproxy ./cmd/mitmproxy   # прод-сборка
```

Целевая прод-платформа — **linux/amd64** (VPS / Docker `scratch`, ~10–15 МБ).
Разработка и тесты — на Windows.

## Что важно помнить про производительность

Сам балансировщик почти не узкое место: 95% времени запроса — апстрим-прокси и
целевой сайт. Go выбран за горутины («одно соединение — одна горутина»), CONNECT
и `io.Copy` из коробки, один бинарник. Rust дал бы 20–40% по памяти/задержкам,
но только на десятках тысяч конкурентных туннелей — до ~10k разницы не будет.
