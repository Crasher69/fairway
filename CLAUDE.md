# Fairway — адаптивный прокси-балансировщик с MITM

Один статический бинарник на Go (`fairway`): HTTP/HTTPS прокси-сервер, который распределяет
исходящие запросы по пулу апстрим-прокси, сам измеряет их качество для каждого
домена и балансирует на основе этих метрик. Опционально расшифровывает TLS
(собственный CA, как Fiddler) — для просмотра запросов и точных метрик.

## Зачем это (чего нет в готовых решениях)

gost / glider / 3proxy / Squid умеют списки и ротацию, но балансируют статически
(round-robin, least-conn, фиксированные веса). Здесь ключевое — **адаптивный
рейтинг на пару (домен, прокси)**, который сам себя настраивает в рантайме.
Один прокси может быть быстрым для одного сайта и забаненным на другом.

## Модель данных

- **Proxy** — апстрим: схема (http/https/socks5), host:port, креды, метки.
- **List** — именованный набор прокси.
- **Domain** — правило: домен (+ wildcard) → List + настройки:
  - `max_parallel_proxies` — сколько РАЗНЫХ прокси работают на домен разом,
  - `max_conns_per_proxy` — сколько соединений держит один прокси,
  - `mitm: true|false` — расшифровывать или просто туннелировать,
  - `ban_duration` — на сколько выключать прокси после бана.
- **Stats(domain, proxy)** — живут в памяти, периодически сбрасываются на диск:
  connect time, TTFB, throughput, error rate — всё как **EWMA**
  (экспоненциальное скользящее среднее: само забывает старое, память O(1)).

## Алгоритм выбора прокси (`internal/rating`)

Всё сводится к одному числу — **цене**: сколько секунд занял бы через этот
прокси эталонный ответ в 64 КБ.

```
цена = (connect + TTFB) / 1000 + 65536 / скорость
цена /= (1 - доля_ошибок)^2        # ошибки дороже медленности:
                                   # неудачный запрос придётся повторять
```

Все слагаемые — EWMA (alpha 0.25): O(1) памяти на пару, само забывает старое,
чистить нечего. Скорость считается только по ответам **от 32 КБ** — на мелких
тело приходит вместе с первым байтом, знаменатель вырождается и скорость
скачет от нуля до сотен МБ/с.

Порядок выбора:

1. **Забаненные для домена выбывают** целиком.
2. **Непроверенные идут первыми** (меньше 3 замеров). Без этого новый прокси
   не набрал бы статистику и остался бы невидимым навсегда.
3. **Разведка**: с вероятностью `Epsilon` (10%) — случайный из живых.
4. Иначе — **взвешенная лотерея** с весом `(1/цена)^Sharpness`, где
   `Sharpness = 2`.

Почему лотерея, а не «всегда лучший»: победитель забрал бы весь трафик,
упёрся в лимит соединений и деградировал, а его замеры перестали бы отражать
реальность. Почему степень, а не просто `1/цена`: при линейном весе прокси
вдвое дешевле получает лишь вдвое больше запросов — для «выбираем лучшее»
этого мало. Квадрат даёт лидеру ~90% трафика, остальное уходит на разведку.

**Бан ≠ медленно.** Медленный прокси остаётся в ротации с низким весом.
Выключается он только по признакам «мёртв для этого домена»:

- HTTP 403, 429, 451, 407 → бан на `ban_duration`;
- 3 ошибки соединения подряд → бан (успех обнуляет серию).

Бан всегда **только для своего домена**.

**Капча** (`internal/challenge`) — третий признак бана, только в MITM: сайт
отвечает 200 и отдаёт страницу проверки, по туннелю это неотличимо от успеха.
Смотрятся заголовки (`Cf-Mitigated: challenge`, `Location` на `showcaptcha`)
и первые 64 КБ тела. Два правила, ради которых пакет и написан:

- **Ложное срабатывание дороже пропуска** — оно выключает живой прокси.
  Поэтому маркеры двух сортов: сильные (`_cf_chl_opt`, `captcha-delivery.com`,
  `px-captcha`… — бывают только на страницах проверки) и слабые (виджет
  reCAPTCHA стоит и на обычной форме логина). Слабые засчитываются только
  вместе со статусом 403/429/503 или говорящим `<title>`.
- **В сжатое тело надо уметь заглянуть.** gzip и deflate распаковываются из
  обрезанного куска, а brotli и zstd в стандартной библиотеке нет — поэтому
  из `Accept-Encoding` клиента они вырезаются, как делают все MITM-прокси.

Причина бана в панели — `капча: cloudflare`, в живом логе статус
подсвечен как `200 капча`.

Рейтинги переживают перезапуск: `data/ratings.json`, автосохранение раз в 30 с
и при остановке, запись атомарная (во временный файл + rename). Протухшие баны
при загрузке не восстанавливаются.

**Вытеснение.** Пара (домен, прокси), не получавшая запросов сутки
(`DefaultEvictAfter`), забывается перед автосохранением: при правиле `*` с
тысячами доменов таблица иначе росла бы бесконечно, а замеры суточной давности
всё равно ничего не значат — пусть прокси проверяется заново, как новый.
Действующие баны не вытесняются. Метка `lastUsed` ставится уже при создании
пары (она заводится при выборе, до первого замера), иначе свежая запись
выглядела бы «давно не использованной».

**Снять бан руками** — `Registry.Unban`: обнуляет и срок, и серию ошибок, иначе
первая же неудача после снятия вернула бы бан обратно.

## Как узнаём домен

- Обычный HTTP — заголовок `Host`.
- HTTPS без MITM — из `CONNECT host:443`. Дальше видим только байты, поэтому
  метрики = время до первого байта от апстрима + bytes/sec через туннель.
- HTTPS с MITM — видим настоящий HTTP: метод, URL, заголовки, тело, статус.
  Отсюда точный детект бана и per-response метрики.

## MITM (`internal/mitmca`, `internal/forward/mitm.go`)

1. При первом запуске в каталоге данных создаётся корневой CA:
   `fairway-ca.pem` (раздаётся) и `fairway-ca.key` (права 0600).
2. На `CONNECT` с правилом `mitm: true` отвечаем `200 Connection established`,
   поднимаем TLS с клиентом и по SNI на лету выпускаем сертификат домена,
   подписанный нашим CA.
3. Расшифровали → разобрали HTTP → отдельным TLS-соединением через выбранный
   апстрим идём к цели → ответ отдали клиенту и сняли замер с настоящим статусом.

**Имя CA** — `CN=Fairway Local Root CA (<машина>)`, `O=Fairway Proxy`.
Три требования, и все три обязательны: видно продукт, видно что центр
**локальный**, видно машину выпуска (иначе две установки дадут одинаково
названные, но разные CA, и админ не разберётся). Мимикрия под настоящие
удостоверяющие центры недопустима — это превращает инструмент во вредоносный.

**Ключи — ECDSA P-256.** Ключ листа генерируется один раз при старте и
переиспользуется для всех доменов: генерация ключа на каждое рукопожатие
добавляла бы задержку на ровном месте. Так делают все MITM-прокси.
Сертификаты доменов живут в LRU-кэше на 2048 записей.

**Одно клиентское соединение — одно соединение к цели.** Пула нет намеренно:
HTTP/1.1 внутри соединения последователен, зато замеры точные. ALPN с обеих
сторон ограничен `http/1.1` — HTTP/2 здесь не разбирается.

**Повтор запроса при смерти keep-alive.** Цель закрывает простаивающее
соединение молча, и первый запрос после паузы попадает в мёртвое. Тело до
`ReplayBodyLimit` (1 МиБ, флаг `-replay-body`) читается в память, и запрос
повторяется на новом соединении. Два ограничения, оба обязательны:

- повтор только если от цели **не пришло ни байта** (`received` из
  `exchange`): получив начало ответа, нельзя знать, выполнен ли запрос,
  а повторять POST вслепую опасно;
- тело больше лимита уходит потоком и не повторяется — клиент получит 502,
  как раньше.

Остаточный риск: цель приняла запрос целиком, выполнила и умерла, не ответив.
Тогда повтор выполнит его дважды. Так же ведёт себя `http.Transport` в Go
при `Idempotency-Key`, и для прокси это приемлемая цена против 502 на каждом
первом POST после паузы.

Известные ограничения:
- **Certificate pinning** — банковский и мобильный софт не пройдёт.
  Отсюда per-domain переключатель `mitm: false` → прозрачный туннель.
- **Проверка отзыва.** У приватного CA нет CRL и OCSP, и клиенты, которые
  требуют проверку отзыва, будут ругаться: `curl` на Windows (schannel) падает
  с `CERT_TRUST_REVOCATION_STATUS_UNKNOWN`, лечится `--ssl-no-revoke`.
  Браузеры для приватных корней отзыв не проверяют и работают нормально.
- **Firefox, Java, Python** имеют своё хранилище сертификатов — CA туда
  добавляется отдельно (в Firefox есть флаг доверять системному хранилищу).
- Раскатка CA по сети: `fairway -export-ca fairway-ca.crt` → Windows
  «Доверенные корневые центры», в домене — групповой политикой.
- **На keep-alive соединении время установки не измеряется** — замер помечается
  `Reused`, и ноль не попадает в среднее время подключения.


## Конфиг (`config.json`)

Создаётся автоматически при первом запуске, перечитывается на лету
(`internal/config.Watcher`, опрос mtime+size раз в 2 с). Битая версия **не
применяется**: в работе остаётся предыдущая, ошибка пишется в лог один раз.

```json
{
  "defaults": {
    "list": "residential",
    "allow_direct": false,
    "max_parallel_proxies": 0,
    "max_conns_per_proxy": 32,
    "mitm": false,
    "ban_duration": "5m"
  },
  "proxies": [
    {
      "name": "p1",
      "scheme": "socks5",
      "host": "1.2.3.4",
      "port": 1080,
      "login": "user",
      "password": "pass",
      "country": "RU",
      "comment": "куплен до декабря"
    }
  ],
  "lists": [{"name": "residential", "proxies": ["p1"]}],
  "domains": [
    {"pattern": "example.com", "list": "residential", "max_parallel_proxies": 3},
    {"pattern": "*.example.com", "list": "residential", "mitm": true}
  ]
}
```

Что важно знать про семантику:

- **Прокси разложен по полям**, а не задан строкой: так его правят в панели и
  так же прокси и продают — «ip:port:логин:пароль». Строку целиком можно
  положить в `url`, при загрузке она разберётся на поля, а само `url` из файла
  исчезнет. `country` и `comment` ни на что не влияют, но без них список из
  полусотни адресов не читается.
- **Два разных лимита, их легко перепутать.** `max_parallel_proxies` — сколько
  РАЗНЫХ прокси листа работают на домен одновременно (рабочий набор);
  `max_conns_per_proxy` — сколько соединений держит один прокси (чтобы не
  задушить лидера рейтинга).
- **Наследование:** `0` — «не задано, взять из `defaults`», `-1` — «явно без
  ограничения». Для `mitm` то же самое даёт отсутствие поля (`null`).
- **Подбор правила:** точное имя → самый длинный `*.суффикс` → `*` →
  `defaults.list`. Регистр и точка в конце FQDN не важны. `*.example.com` не
  покрывает сам `example.com`.
- **`allow_direct`** разрешает ходить напрямую, когда правило не подобрано.
  По умолчанию `false`, и это осознанно: иначе домен без правила молча уйдёт
  с реального IP. При `false` такой запрос получает 503.
- **Неизвестные поля запрещены** (`DisallowUnknownFields`): опечатка в имени
  ключа не должна молча игнорироваться.
- `-upstream host:port` (флаг, можно повторять) собирает временный конфиг
  из командной строки и полностью игнорирует файл — для быстрой проверки.

Прокси при hot-reload сопоставляются **по имени**: если имя и адрес не
изменились, объект переиспользуется вместе со счётчиками и (с этапа 3)
рейтингом. Поэтому переименование прокси = сброс его статистики.

## Админка (`internal/admin`, `internal/stats`)

Тот же процесс и тот же бинарник, отдельный порт (по умолчанию `127.0.0.1:8081`).

- `GET /api/overview` — версия, аптайм, счётчики, корневой CA, размер кэша сертов
- `GET /api/domains` — домены, по которым реально шёл трафик (не паттерны!)
- `GET /api/domains/{domain}` — правило и таблица прокси: активные соединения,
  connect, TTFB, скорость, доля ошибок, цена, ожидаемая доля трафика, бан
- `GET /api/events?domain=&limit=` — живой лог из кольцевого буфера
- `GET /api/stream?domain=` — SSE-поток событий
- `GET /ca` — корневой сертификат для импорта

**Реалтайм через SSE, а не WebSocket**: поток односторонний, переподключение
браузер делает сам, отлаживается обычным `curl -N`.

**Доля трафика в таблице считается ровно так же, как её считает `Select`,
включая разведку**: `epsilon/живых + (1-epsilon)·вес/сумма`. Без слагаемого
разведки лидер на локальном стенде показывал 99.99% вместо реальных 93%.

**Фронт без сборки и без зависимостей**: ванильный JS, график рисуется руками
в SVG. Файлы в `internal/admin/web`, вшиты через `//go:embed` — на выходе
по-прежнему один бинарник.

Что важно в дизайне панели:

- **Светлая тема по умолчанию, тёмная — по системной настройке или кнопкой**
  в шапке (`html[data-theme]`, запоминается в localStorage). Все цвета —
  CSS-токены; в разметке и JS hex-значений нет, кроме палитры графика.
- **Подсказка «как начать»** показывается, пока не пошёл трафик: четыре шага
  с отметками, что уже сделано, и адрес прокси (`proxy_addr` из overview) —
  без него человек не знает, что прописать в браузере.
- **Цвет серии закреплён за прокси** в порядке первого появления и не меняется
  при перерисовке; палитра фиксированная, соседние оттенки различимы при
  дальтонизме. Тот же цвет — у полоски доли трафика в таблице.
- **График по номеру запроса, а не по времени**: трафик идёт неровно, и при
  паузе в минуту все точки сплющились бы у правого края. Подсказка при
  наведении показывает ближайший запрос и последний замер остальных прокси.
- **Удаление — с подтверждением, успех — с уведомлением.** Раньше правка
  молча перерисовывала таблицу, и было непонятно, применилась ли она.
- **Наследуемые значения в таблице правил показываются приглушённо**, а не
  прочерком: «—» читалось как «не задано», хотя лимит действует из общих.

**Кольцо событий — витрина, а не хранилище**: 5000 последних запросов в памяти,
при перезапуске теряется. Долговременные выводы делает рейтинг.

**Безопасность по умолчанию**: bind только на loopback, доступ по токену
(`-admin-token`, пустой — генерируется случайный и печатается в лог ссылкой).
Токен принимается из query (сохраняется в cookie), заголовка `Authorization`
или cookie. При bind не на loopback в лог пишется предупреждение.

## Правила проекта

- **Только стандартная библиотека там, где это разумно.** Зависимости — по
  необходимости и с оглядкой на кросс-компиляцию.
- **Никакого cgo.** Если понадобится SQLite — только `modernc.org/sqlite`
  (чистый Go). Для MVP хватит JSON-файлов.
- Хранение конфига и снапшотов рейтингов — JSON на диске, hot-reload без рестарта.

## Что важно помнить про производительность

**Обычный HTTP идёт через пул соединений к апстриму** (`Upstream.Transport`):
один `http.Transport` на апстрим, к http-прокси соединения общие для всех
целей, к socks5 и direct — по адресу цели. Замеры снимаются через
`httptrace`: `ConnectStart`/`GotConn` дают время подключения и признак
переиспользования, `GotFirstResponseByte` — первый байт. `DisableCompression`
обязателен: прокси передаёт тело как есть. Выбывший из конфига апстрим
закрывает простаивающие соединения (`CloseIdle` из `Pool.Apply`). До пула
обычный HTTP был в 14 раз медленнее туннелей, теперь в 2,5.

Сам балансировщик почти не узкое место: 95% времени запроса — апстрим-прокси и
целевой сайт. Go выбран за горутины («одно соединение — одна горутина»), CONNECT
и `io.Copy` из коробки, один бинарник. Rust дал бы 20–40% по памяти/задержкам,
но только на десятках тысяч конкурентных туннелей — до ~10k разницы не будет.

## Правка конфига из панели (`internal/admin/write.go`)

- `GET /api/config` — текущий конфиг целиком
- `POST /api/config/reload` — перечитать файл (если правили руками)
- `POST /api/proxies`, `PUT /api/proxies/{name}`, `DELETE /api/proxies/{name}`
- `POST /api/proxies/bulk` — `{names, action: delete|add_to_list|remove_from_list, list}`
- `PUT /api/lists` (создать или заменить), `PUT /api/lists/{name}` (правка,
  в том числе переименование), `DELETE /api/lists/{name}`
- `PUT /api/domains`, `DELETE /api/domains/{pattern}`
- `PUT /api/defaults`
- `POST /api/domains/{domain}/unban/{proxy}` — снять бан (это не правка
  конфига, а состояние рейтинга; 404, если бана не было)

Дисциплина правок, и она важнее самих ручек:

1. Правки идут **по очереди** (mutex в `Editor`) — иначе две одновременные
   потеряли бы друг друга.
2. Меняется **копия** конфига: живой в этот момент читают обработчики запросов.
3. Результат **проверяется целиком до записи**. Битый конфиг не должен попасть
   на диск даже на мгновение — его подхватит сторож и начнёт ругаться.
4. Файл остаётся **единственным источником правды**: сохранили и применили
   теми же путями, что и ручную правку.

При удалении прокси он сначала вычищается из всех листов — иначе проверка
честно упала бы на ссылке в никуда, и пользователь увидел бы невнятную ошибку
вместо ожидаемого удаления. При переименовании листа так же чинятся ссылки в
правилах доменов и лист по умолчанию.

**Массовые действия — одна правка на всю пачку.** Полсотни отдельных запросов
были бы полусотней перезаписей файла, и на середине конфиг мог бы оказаться
применённым наполовину. Проверка целиком тоже одна: удалить последний прокси
листа нельзя, и конфиг на диске не меняется.

**Сторож не применяет запись панели второй раз.** `Editor` после `Save`
вызывает `Watcher.MarkApplied`, и текущая версия файла считается уже
применённой. Без этого каждая правка из панели давала лишнее применение и
строку «конфиг перечитан» в логе.

**Ноль в правиле домена не пишется в файл** (`omitempty`): он значит
«наследовать из defaults», а явный `"ban_duration": "0s"` человек прочтёт как
«баны выключены».

При `-upstream` конфиг собран из флагов и сохранять его некуда — `Editor` там
не создаётся, а запись отвечает 501.

## Прод

- `Dockerfile` — сборка на `scratch`. **Корневые сертификаты обязательны**:
  без них MITM не проверит сертификат цели. Плюс zoneinfo, иначе время только
  в UTC. Пользователь numeric (65534), в `scratch` нет `/etc/passwd`.
- `build.sh` — кросс-сборка под linux amd64/arm64, windows, macOS.
  Версия через `-ldflags -X main.version`.
- `GET /healthz` — без токена, для проб Docker и systemd.
- `/api/overview` отдаёт горутины и кучу: по горутинам видно утечку соединений.
- `cmd/loadgen` — нагрузочный генератор. Считает статусы: без этого отказы
  выглядели бы рекордной скоростью, 503 отдаётся мгновенно.

Цифры и методика — `docs/BENCHMARK.md`.

## Установка CA в хранилище системы (`internal/mitmca/trust.go`)

- `GET /api/ca` — subject, срок, отпечатки, стоит ли в хранилище и где
- `POST /api/ca/install` / `POST /api/ca/uninstall`

Два правила, которые здесь важнее удобства:

1. **Только пользовательское хранилище, не машинное.** Прав администратора
   не нужно, и затронут один пользователь, а не вся машина.
2. **Через штатные утилиты ОС** — `certutil -user -addstore` на Windows,
   `security add-trusted-cert` на macOS. Лезть в хранилища самостоятельно —
   верный способ оставить систему в неконсистентном состоянии.

На Linux автоматической установки нет: там всё зависит от дистрибутива и
требует root. Панель показывает инструкцию вместо кнопки.

Удаление сделано наравне с установкой намеренно: оставлять в системе живой
корневой сертификат после того, как инструмент больше не нужен, — плохая
гигиена, и убрать его должно быть так же просто, как поставить.

**CA не зашит в бинарник и не может быть зашит.** Он создаётся при первом
запуске в каталоге данных, у каждой установки свой. Общий приватный ключ
внутри публичного бинарника — это Superfish и eDellRoot: любой, кто скачал
программу, смог бы подписывать сертификаты, которым доверяет чужая сеть.

**Windows опознаёт сертификаты по SHA-1, а не по SHA-256.** `certutil` с
SHA-256 молча не находит ничего, поэтому для поиска и удаления используется
`Thumbprint()` (SHA-1), а человеку показывается `Fingerprint()` (SHA-256).
Проверка идёт через `-store`, а не `-verifystore`: второй строит цепочку и
пробует узнать статус отзыва, а у приватного CA нет ни CRL, ни OCSP — и
установленный сертификат выглядел бы отсутствующим.

Проверяются оба хранилища, пользовательское и машинное: сертификат мог
поставить кто-то руками, и «не установлен» при живом сертификате в машинном
хранилище — худшее, что панель может сообщить.

## Импорт прокси списком (`internal/config/importer.go`)

`POST /api/proxies/import` принимает текст, по строке на прокси. Понимает то,
в чём прокси реально продают:

```
1.2.3.4:1080                     без авторизации
1.2.3.4:1080:логин:пароль        самый ходовой формат прайсов
логин:пароль@1.2.3.4:1080        встречается не реже
socks5://логин:пароль@1.2.3.4:1080
```

Решения, которые здесь важны:

- **Схема из строки важнее схемы по умолчанию.** Прислали `socks5://` —
  значит, человек знает, что это socks5.
- **Имена присваиваются сами** (`префикс-N`), с обходом уже занятых: набивать
  полсотни имён руками никто не станет.
- **Дубликаты по адресу пропускаются, а не заменяют запись.** Повторная
  вставка того же списка не должна ничего ломать.
- **Отчёт построчный, с номерами строк.** «Добавлено 47 из 50» заставило бы
  искать три плохие строки глазами.
- **Одна правка конфига на весь список.** Полсотни отдельных POST — это
  полсотни перезаписей файла, и на середине список мог бы оказаться применён
  наполовину.
- Если не разобрана ни одна строка, конфиг не переписывается вовсе, но отчёт
  человек получает.

## Иконка (`internal/brand`, `cmd/mkicon`)

Флажок на грине: зелёный скруглённый квадрат, белый шест и три белые полосы
разной длины. Полосы — одновременно флаг (fairway — участок поля для гольфа,
флажок отмечает лунку) и шкала рейтинга. На 16 пикселях читается как флаг.

- **Растр рисуется в Go без библиотек**: фигуры — скруглённый прямоугольник и
  капсулы, считаются по расстоянию до отрезка, сглаживание суперсэмплингом 4×4.
  Тот же рисунок лежит в `internal/admin/web/icon.svg` для панели и favicon;
  геометрия в двух местах повторяется один в один — **менять вместе**.
- **`.syso` собирается своим кодом**, а не `rsrc`/`go-winres`: объектный
  COFF-файл с секцией `.rsrc`, деревом ресурсов (RT_ICON × 6 размеров +
  RT_GROUP_ICON), таблицей перемещений `ADDR32NB` и одним символом секции.
  Линковщик Go подхватывает `rsrc_windows_<arch>.syso` из каталога main-пакета
  сам. Мелкие размеры — классический DIB, 256 — PNG.
- **Результаты генерации лежат в репозитории**: `go build` не должен требовать
  `go generate`. После правки рисунка — `go generate ./cmd/fairway`.
- Проверка, что exe получил значок: `[System.Drawing.Icon]::ExtractAssociatedIcon`
  в PowerShell или свойства файла в проводнике. В тестах объектный файл
  разбирается стандартным `debug/pe` — тем же, что читает линковщик.
- Иконка только у Windows-сборки: macOS и Linux требуют бандла или `.desktop`,
  у голого бинарника там значка не бывает.
